# Codex support alongside Claude Code

Status: proposal, for Codex to implement. This fills in the "Codex install" item of Phase 2 in `2026-11-12-code-check-design.md`. Authority order is unchanged: this spec, then the Codex spike it asks for (which overrides this spec's prose where they disagree about what Codex does), then the plan.

## Intent

Make the review skills usable from Codex without touching how they run in Claude Code. The deterministic CLI (diff parsing, finding validation, anchoring, policy, state, `git`/`gh`) is shared. Only the pieces that talk to an agent runtime are duplicated, and those are generated from the same sources so they cannot drift. The release that ships this is 1.0.0.

## Non-goals

- Changing anything Claude Code sees. `skills/`, `agents/`, `hooks/` and `.claude-plugin/` stay byte-identical apart from the version fields.
- A Codex runner for the unattended path (`loop`, `run_pr`, which shell out to `claude -p`). They stay Claude-only in 1.0.0 and the install doc says so. A `codex exec` runner is its own piece with its own spike.
- Forking the CLI, the evals or the golden set.
- Changing the protected merge guard (`shadow/queue.py`, `commands/handoff_queue.py`, `tests/test_handoff_queue.py`).

## What is not yet known

The facts about Codex below come from third-party guides, not OpenAI's documentation, and some conflict. Phase 0 settles them. Do not build on them before then.

- Skills are SKILL.md folders in `.agents/skills/` (repository) or `$HOME/.agents/skills/` (user), selected with `$skill-name`.
- Custom agents are TOML files in `.codex/agents/<name>.toml`, gated by a feature flag (`multi_agent` or another name) with limits under an `[agents]` table.
- Configuration is `~/.codex/config.toml`; instructions are `AGENTS.md`; non-interactive runs use `codex exec`.
- The default model is `gpt-5-codex` (refreshed June 2026) with `gpt-5-codex-mini` for lighter work; newer names (`gpt-5.4`, `gpt-5.5`) are reported inconsistently. The source of truth is OpenAI's Codex models page.
- Unknown: whether a Codex agent can be restricted to reading the checkout and writing one directory. The Claude agents have the tool allowlist `Read, Grep, Glob, Write`; Codex may offer only sandbox modes.

## Layout

```
codex/skills/<name>/SKILL.md              generated from skills/<name>/SKILL.md
codex/agents/<name>.toml                  generated by agentgen, one per reviewer role
AGENTS.md                                 development guidance for Codex
docs/INSTALL-CODEX.md                     install, uninstall, configuration, first run
docs/superpowers/spikes/<date>-codex.md   what Codex actually does (Phase 0)
```

`CODE_CHECK.md` is shared: both agent sets read it first, as the Claude agents do.

## Design

**Models.** Add a `[codex_models]` table with the same keys as `[models]` (`aggregator`, `language_experts`, `reviewers`, `deep`, `security`, `performance`, `judge`, `per_language`). `model_for()` gains a `runtime` argument that defaults to `"claude"`, so every existing call is unchanged. `MODEL_NAME` already accepts OpenAI-style names. The defaults are by tier, to be confirmed in the spike:

| Claude | Roles | Codex default |
|---|---|---|
| opus | aggregator, security, judge | the strongest available model, high reasoning effort |
| sonnet | architect, skeptic, pragmatist, performance, deep | `gpt-5-codex`, medium reasoning effort |
| haiku | the language experts | `gpt-5-codex-mini` |

Defaults live in code and are overridable in user config. `codex_models` follows the same rule as `models`: a repo's `.code-check.toml` may set it only where it may set `models`, and the security-sensitive keys stay rejected there.

**Agents.** `agentgen.py` renders one set of role prompts to a target. `gen-agents --target codex --out codex/agents` writes TOML (name, description, model, reasoning effort, instructions, sandbox); the default target is Claude and its output must not change. The prompt text is shared; only the wrapper differs. The existing drift test is duplicated for the Codex output.

**Skills.** Generate `codex/skills/` from `skills/` with a fixed substitution table for the Claude-specific constructs: the `${CLAUDE_PLUGIN_ROOT}` path, the `Agent` call with `subagent_type` `code-check:<member>`, and any `AskUserQuestion`. A static test fails if a Claude-only construct survives in the Codex output, and `tests/test_plugin_static.py` cross-checks the Codex skills against the real argparse parser as it does for the Claude ones. Generating instead of copying avoids the duplicated step sequences that `CODE_CHECK.md` item 1 flags.

**Install.** `installer/` gains a `--target codex`. It copies `codex/skills` and `codex/agents` into the Codex directories the spike confirms, records a receipt, and uninstalls only what the receipt lists, as the Claude path does. At install time it writes the absolute CLI path into the skills, since Codex has no `CLAUDE_PLUGIN_ROOT`. `bin/code-check` already bootstraps its own venv and falls back to `~/.local/share/code-check`, so the CLI needs no change. `doctor` gains a `codex` check.

**AGENTS.md.** Short. Read `CLAUDE.md` for the architecture and invariants (they apply to Codex too); the commands to run (`pytest`, `ruff`, `node --test`, `gen-agents --target codex`); generated files are never hand-edited. It must not restate `CLAUDE.md`, so the two cannot disagree.

## Phases

0. **Spike.** Someone with Codex installed records: where skills are discovered; the custom-agent TOML schema and feature flags; whether a named agent can be dispatched in parallel and given a restricted sandbox; how `codex exec` treats permissions; the current model names. Output: the spike file. If a panel of named parallel subagents is not possible, stop and re-plan: the fallback is a CLI-orchestrated panel, which is a larger design.
1. **Guidance.** `AGENTS.md` and this spec as confirmed. No behaviour change.
2. **Config and generation.** `codex_models`, `--target codex`, generated agents and skills, tests. Show that `agents/` and `skills/` are unchanged and `eval --replay` passes.
3. **Install.** Installer target, uninstall, doctor, `docs/INSTALL-CODEX.md`, a README section that links to it. `tests/test_readme.py` checks the README against the CLI and config keys, so update them together.
4. **Release 1.0.0.** Bump every place the version lives: `VERSION`, `pyproject.toml`, `package.json`, `package-lock.json` (both entries), `.claude-plugin/plugin.json`, `.claude-plugin/marketplace.json`, `src/codecheck/__init__.py`. Add `codex/` to the paths in rule 3 of `CODE_CHECK.md`. Tag after merge.

Ship as two PRs: Phases 0 and 1, then Phases 2 to 4.

## Risks

| Risk | Level | Mitigation |
|---|---|---|
| Codex cannot dispatch named parallel subagents as the review skill needs | High | The spike decides; stop and re-plan |
| Reviewer agents cannot be limited to reading plus writing one directory, and they read untrusted PR text | High | Do not loosen the sandbox silently. Either document the weaker guarantee in `INSTALL-CODEX.md` or make a restricted sandbox a condition for shipping |
| Guessed model names are wrong or retired | Medium | Defaults come from the spike and are overridable |
| A Claude regression | Medium | Byte-identical `agents/` and `skills/`; replay gate |
| Skill drift between targets | Medium | Generate, with a drift test |
| The merge guard accepts only one-step patch bumps, so 1.0.0 is refused | Low | The guard governs unattended `handoff-round`; do this release by hand and do not edit the guard |

## Testing

Claude outputs: the existing drift tests pass with no regenerated file. Codex outputs: drift test for `codex/agents` and `codex/skills`; no Claude-only construct in either; every `code-check` subcommand and flag a Codex skill uses exists in the argparse parser. Config: `codex_models` defaults, per-language override, a repo cannot set what `models` forbids it to set, `model_for(..., runtime="claude")` unchanged. Installer (`node --test`): Codex install writes the receipt and the absolute path; uninstall removes only receipt entries and refuses anything outside the Codex skills and agents directories; the Claude install is unchanged.

## Open decisions

- Whether the `codex exec` runner for `loop` and `run_pr` joins 1.0.0 or follows it. This spec says follow.
- Whether a Codex-side live eval is wanted to judge the model mapping, beyond configuring it. It costs tokens and is advisory, like `eval --calibrate`.
