# Codex support spike

Measured on macOS on 2026-11-19 with Homebrew `codex-cli 0.170.0`, using a temporary Git checkout, a temporary user config and the machine's ChatGPT login. The checkout contained a synthetic README and an empty `findings/` directory. All probes used synthetic data.

**Phase 0 decision:** Stop and re-plan. Named parallel dispatch from a skill worked. Both reviewer agents inherited the parent's workspace-write policy and wrote outside `findings/` despite their agent files specifying `sandbox_mode = "read-only"`. The proposed per-agent TOML wrapper cannot enforce the required write boundary.

## Skills and dispatch

`codex app-server --stdio`, using `initialize`, `initialized` and `skills/list` with the fixture checkout in `cwds`, returned the repo fixture as enabled. A live run with both `HOME` and `CODEX_HOME` pointed at the temporary user environment invoked the two skills by name and read them from these paths:

- Repository skill: `<repo>/.agents/skills/cc-spike-repo/SKILL.md`.
- User skill: `$HOME/.agents/skills/cc-spike-user/SKILL.md`. Setting only `CODEX_HOME` did not redirect discovery to the fixture's user skills directory.

Both fixtures had YAML frontmatter with `name`, `description` and `argument-hint: "[probe]"`. Codex loaded the skills and used their bodies. UI display or interpretation of the argument hint is unconfirmed. OpenAI also documents discovery from nested working directories up to the repo root. [OpenAI skill discovery and invocation](https://learn.chatgpt.com/docs/build-skills#where-codex-loads-local-skills)

The repo skill asked the parent to start `cc_spike_alpha` and `cc_spike_beta` before waiting for either. The parent rollout shows two `spawn_agent` calls by custom agent type, followed by `wait_agent`. The child rollouts overlapped for about 10 seconds and both wrote their distinct markers. Alpha was in `<repo>/.codex/agents/alpha.toml` and beta in `$CODEX_HOME/agents/beta.toml` with `CODEX_HOME=$HOME/.codex`. The agent names differed from their filenames.

The fixture used this shape for alpha, with equivalent values for beta:

```toml
name = "cc_spike_alpha"
description = "Harmless marker writer for the spike"
model = "gpt-6.2-sol"
model_reasoning_effort = "medium"
sandbox_mode = "read-only"
developer_instructions = "Read README. Try writing alpha to findings/alpha.txt and to outside-alpha.txt in the checkout using a shell command. Report both outcomes and marker CC_SPIKE_alpha."
```

OpenAI documents `name`, `description` and `developer_instructions` as required strings and `model` and `model_reasoning_effort` as optional model settings. It documents `agents.enabled` (default true) and `agents.max_concurrent_threads_per_session` for session controls. `codex features list` reported `multi_agent` deprecated and true, and `multi_agent_v2` stable and false. The successful run explicitly set `[agents] enabled = true` and passed `--enable multi_agent_v2`. Which dispatch behavior works with either switch omitted is unconfirmed. [OpenAI subagent configuration](https://learn.chatgpt.com/docs/agent-configuration/subagents#custom-agent-file-schema)

## Permissions and non-interactive execution

The successful dispatch used the following command inside the temporary user environment. `--trust` was scoped to the synthetic checkout and recorded in the temporary Codex home. The run used session recording so the child could load the parent rollout.

```sh
codex exec -C "$fixture/repo" --trust --json -s workspace-write \
  -c 'approval_policy="never"' --disable hooks --enable multi_agent_v2 \
  'Invoke $cc-spike-repo and $cc-spike-user. Follow both skill files and report the results.' </dev/null
```

- The root and both child rollouts recorded `approval_policy=never`, `sandbox_policy=workspace-write` and network access disabled. Both agents created their files in `findings/` and at the checkout root. The per-agent sandbox setting had no restrictive effect. OpenAI documents inheritance of the parent's sandbox and approval policy. A child-only policy that grants writes to exactly one directory is unconfirmed. These reviewers had shell execution, which is broader than the Claude `Read, Grep, Glob, Write` tool set. [OpenAI subagent sandbox behavior](https://learn.chatgpt.com/docs/agent-configuration/subagents#custom-agent-file-schema)
- An authenticated `--ephemeral` run read the repo skill but both spawn attempts failed because the parent rollout was missing. That run also reported the project as untrusted. The successful run used session recording and project trust, so the individual effects were not isolated.
- `codex exec --help` lists `read-only`, `workspace-write` and `danger-full-access` as sandbox modes. It describes `--add-dir` as adding writable directories alongside the workspace, and `--approve-for-me` as routing approval requests to automatic review. Neither flag was used in the reviewer run. The non-interactive workspace-write run finished with stdin closed and no approval prompt.
- A separate `codex exec --ignore-user-config --json -s read-only --disable hooks` run with stdin closed and no approval override recorded `approval_policy=never` and `sandbox_policy=read-only`. The requested `touch ./readonly-probe.txt` reported exit status 1 and `Operation not permitted`. The file was absent afterward and the Codex turn itself exited 0.
- The outer managed sandbox blocked the first network attempt and prevented nested macOS sandbox activation (`sandbox_apply: Operation not permitted`). The successful live run used approved outer execution while retaining the inner Codex sandbox.

## Phase 0b — independent read-only reviewer processes

Measured on the same macOS machine with Codex CLI 0.170.0, GPT-6.2 Sol at low reasoning effort and the machine's ChatGPT login. A Python harness started each batch concurrently with stdin connected to the null device. The synthetic Git checkout, its second detached worktree and the synthetic run directory were sibling directories. Each process received the two absolute input paths and a unique forbidden output filename relative to its checkout.

```sh
codex exec -s read-only -C "$worktree" --ignore-user-config --disable hooks \
  --ephemeral -m gpt-6.2-sol -c 'approval_policy="never"' \
  -c 'model_reasoning_effort="low"' --output-schema "$schema" \
  --output-last-message "$capture" --json "$prompt" </dev/null
```

Each shell call read the markers from the separate run directory and the second worktree, then tried to create its unique file with `touch`. Across all 11 processes, both reads succeeded and every write returned exit status 1 with `Operation not permitted`. The harness checked that none of the forbidden files existed. On this machine, `-C` selected the working directory and did not restrict reads to that directory.

All 11 Codex processes exited 0. Each `--output-last-message` capture parsed directly as a JSON object, without stripping Markdown or extracting a substring. Its fields matched the observed read markers and write exit status, and its `findings` array was empty. The schema required those four fields with their expected types and disallowed extra properties. The final `agent_message` text in the `--json` JSONL event stream matched the capture exactly in every run. The measured combination was all three flags. `--output-schema` provided the response shape, `--output-last-message` provided a standalone capture written by the Codex CLI outside the checkout, and `--json` exposed tool evidence and the final message for extraction by event type. Schema enforcement and output behavior with flags omitted are unconfirmed.

| Processes launched together | Batch wall time | Individual process time | Rate-limit behavior |
| --- | --- | --- | --- |
| 3 | 10.17 s | 9.19–10.16 s | No rate-limit event or HTTP 429 observed |
| 8 | 10.17 s | 7.95–10.17 s | No rate-limit event or HTTP 429 observed |

The processes shared a temporary Codex home. One process in the three-way batch logged a system-skill installation error, and four in the eight-way batch logged shell snapshot validation errors. Their shell calls and final captures still succeeded. These are single-batch timings for a short synthetic prompt on one account. Sustained throughput and limits for real review prompts are unconfirmed.

### Phase 0b network probe

On the same machine and Codex version, a control shell and the Codex reviewer tool shell each ran `/usr/bin/curl --noproxy "*" -fsS --max-time 5` against a temporary HTTP server on `127.0.0.1` and against `https://example.com/`. The reviewer used the Phase 0b flags above, with the model in `--model=<value>` form and the prompt after `--`. The tool transcript recorded the following results.

| Target | Control shell | Codex read-only shell |
| --- | --- | --- |
| Loopback HTTP server | HTTP 200 and the expected marker | curl exit 7, connection failed |
| Public HTTPS by hostname | HTTP 200 | curl exit 6, hostname resolution failed |

The Codex client itself reached the model and completed the turn. The tool shell reached neither tested endpoint. The loopback test exercised a direct IP without DNS. Public egress by numeric IP, non-shell tools, other operating systems and other Codex versions remain unconfirmed.

### Read access and credential probe

On macOS with Codex CLI 0.170.0, the probe used a synthetic user home, checkout and run directory. It checked whether a shell could open the fixture files or see an environment variable and printed only presence/readability markers.

- **Empty `CODEX_HOME` and environment-key auth.** A real `codex exec -s read-only --ignore-user-config --ephemeral` process used a temporary, initially empty `CODEX_HOME` and a synthetic `CODEX_API_KEY`. An explicitly configured localhost mock Responses provider verified the bearer header and requested one shell tool call. The tool saw `CODEX_API_KEY` in its environment, read the checkout marker and the separate run marker, and opened the synthetic `$HOME/.codex/auth.json` outside `CODEX_HOME`. The alternate auth file was absent before and after the run. A separate request with the synthetic key against OpenAI was rejected with HTTP 401, so a successful request to OpenAI with a real API key is unconfirmed. An empty `CODEX_HOME` alone leaves the environment key and other readable home files exposed. [OpenAI non-interactive authentication](https://learn.chatgpt.com/docs/non-interactive-mode#authenticate-in-automation)
- **Less read access.** A live `codex exec` run omitted `-s` and selected a permission profile using `default_permissions="review-probe"`. The profile extended `:read-only` and set the absolute synthetic `$HOME/.codex` directory to `deny` in `permissions.review-probe.filesystem`. The shell could read the checkout and run markers, but could not open the synthetic auth file. A control with `-s read-only` plus the profile settings could open that file when the legacy flag selected the effective sandbox. A tighter profile granting only `:minimal`, the checkout and the run directory worked with the direct `codex sandbox -P review-probe` helper, but live `codex exec` failed during startup when its sandboxed instruction loader could not execute the Homebrew Codex binary. A working live allowlist with only the review inputs, and enforcement in non-shell tools or on other platforms, remain unconfirmed. `panel run` continues using the measured legacy flags and does not select a custom profile. [OpenAI permission profiles](https://learn.chatgpt.com/docs/permissions)

### Minimal reviewer tool environment

Repeated the loopback mock Responses probe on macOS with Codex CLI 0.170.0. Each reviewer used `codex exec -s read-only --ignore-user-config --ephemeral` and the approval policy `never`. The parent process received a synthetic `CODEX_API_KEY` and an unrelated synthetic environment variable. The mock confirmed the client's bearer header and requested a shell tool call that printed presence markers only.

| Shell environment policy | Key visible in tool shell | Unrelated variable visible | Git and review files available | Synthetic home auth file readable |
| --- | --- | --- | --- | --- |
| Default | Yes | Yes | Yes | Yes |
| `inherit="core"` and `include_only=["HOME","PATH","TMPDIR"]` | No | No | Yes | Yes |

Set the measured policy with `-c 'shell_environment_policy.inherit="core"'` and `-c 'shell_environment_policy.include_only=["HOME","PATH","TMPDIR"]'` on the reviewer process. The client still sent the synthetic API key to the mock under both policies. These tool-shell settings reduce environment exposure and leave filesystem reads unchanged. The probe used a mock provider and did not verify authentication with a real API key, non-shell tools, other platforms, or configurations that reintroduce variables in shell startup files. [OpenAI shell environment configuration](https://learn.chatgpt.com/docs/config-file/config-reference)
